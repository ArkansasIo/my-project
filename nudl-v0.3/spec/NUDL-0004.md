# NUDL Language Specification Draft 0004

Status: design draft for the NUDL 0.4 language surface. This document expands the language design; it does not claim that compiler 0.3 implements these features.

## 1. Identity and goals
NUDL is a standalone, typed programming and native data language. It defines its own source grammar, type system, module system, runtime model, diagnostics, and standard library. Other formats and languages may inspire individual capabilities, but their syntax is not embedded into NUDL.

Goals: readable declarations; explicit types; composable modules; safe data modeling; predictable evaluation; generic reusable APIs; clear diagnostics; deterministic core behavior.

## 2. Source files
- Source extension: .nudl
- UTF-8 source encoding.
- Line endings: LF or CRLF.
- Identifiers: Unicode support is a future compatibility decision; the initial profile uses ASCII letters and underscore at the start, followed by letters, digits, or underscore.
- Comments: // line comments and /* block comments */; nested block comments are not supported initially.
- Semicolons terminate declarations and simple statements. A future formatter may permit omitted terminators under defined rules.

## 3. Lexical elements
Identifiers are case-sensitive. Reserved words include: module, import, as, pub, private, let, var, const, type, struct, class, trait, impl, enum, union, fn, async, await, return, if, else, match, for, in, while, loop, break, continue, true, false, null, none, some, new, self, super, where, requires, throws, try, catch, finally, defer, unsafe, extern, package, namespace, dataset, table, index, key, ref, constraint, query, select, from, filter, group, order, limit, distinct, by, and, or, not, is, mut, static, abstract, override, sealed.

Literal forms: integer, real, scientific real, string, character, boolean, null/none, arrays, tuples, and record literals. Exact numeric ranges and Unicode string indexing are reserved for a later normative profile.

## 4. Type system
Primitive types: Unit, Boolean, Byte, Int8, Int16, Int32, Int64, UInt8, UInt16, UInt32, UInt64, Float32, Float64, Decimal, Char, String, Bytes, Duration, Timestamp, and Never.
Composite types: Array<T>, List<T>, Map<K,V>, Set<T>, Tuple<T...>, Option<T>, Result<T,E>, Range<T>, and function types.
User types: type aliases, structs, classes, enums, tagged unions, traits, and interfaces.
Type parameters may have constraints. Nullability is explicit using Option<T>; implicit nullable references are not part of the design.
Conversions are explicit unless a later specification lists a safe widening conversion.

## 5. Bindings and constants
- let name: Type = expression; creates an immutable binding.
- var name: Type = expression; creates a mutable binding.
- const NAME: Type = constant_expression; creates a compile-time constant.
Type inference may infer a local's type when an initializer exists, but public APIs should state types explicitly.

## 6. Functions
Syntax: fn name<T>(arg: Type) -> ReturnType { ... }
Functions may be public or module-private. Parameters are immutable by default. Mutability is expressed in the parameter type or borrowing mode once those semantics are standardized. Return types are explicit for public functions. Overloading, default arguments, and operator overloads require separate semantic rules and are not assumed in the first implementation.
Async functions use async fn and await only with an async-compatible return type. Effects and cancellation behavior remain to be standardized.

## 7. Structures, classes, traits
struct defines value-oriented data with named fields. class defines identity-bearing objects with fields and methods. enum defines a closed set of named cases. union defines tagged alternatives. trait defines required methods and associated behavior. impl associates methods with a type or implements a trait.
Inheritance is single-base for classes in the proposed profile; traits may be implemented multiple times per type. Composition is preferred over deep inheritance. Constructors use init(...). Destructors/finalizers are not deterministic and must not be used for essential cleanup.

## 8. Modules
A module begins with module path.name;. Imports use import path.name; and optional aliases use import path.name as alias;. Public exports are marked pub. Cyclic imports are rejected in the initial profile. The build resolves modules through declared project roots, not arbitrary implicit filesystem traversal.
Packages group modules and carry version metadata. Remote package installation is not part of compiler 0.3.

## 9. Expressions and operators
Arithmetic: + - * / %.
Comparison: == != < <= > >=.
Logical: and or not.
Bitwise: bit_and, bit_or, bit_xor, bit_not, shift_left, shift_right (operator spellings may change before 0.4 freezes).
Other: assignment =, compound assignments, member access ., safe member access ?., indexing [], range .., type test is, cast as, null coalescing ?? (proposed).
Precedence is defined in the grammar. Evaluation order is left-to-right except where a construct explicitly states otherwise.

## 10. Statements and control flow
Blocks use braces. Conditionals use if/else. Loops include while, for-in, and loop with break/continue. match is exhaustive over enums and tagged unions when the compiler can prove coverage. return exits a function. defer schedules cleanup at scope exit, with ordering specified by runtime documentation.
Loop labels and labeled break are not in the initial profile.

## 11. Arrays and collections
Array<T> is a fixed-length contiguous sequence in the initial runtime proposal. List<T> is a resizable sequence. Indexing is zero-based. Bounds errors return a defined runtime error unless a checked-access operation is used. Slices are half-open ranges [start..end). Mutability, aliasing, and copy behavior must be explicit in the eventual runtime.
Nested arrays are supported as Array<Array<T>>; rectangular multidimensional storage may later be a dedicated Tensor<T, Rank> type.

## 12. Native data declarations
dataset and table declarations are native NUDL constructs, not wrappers around SQL or spreadsheet formats. Schemas define fields, types, keys, references, and constraints. Query syntax must be specified independently and must not silently translate or embed SQL.
Persistence format, transaction isolation, indexing, and migration semantics remain separate specifications.

## 13. Errors and effects
Expected failures use Result<T,E>; optional absence uses Option<T>. try/catch is reserved for exceptional runtime faults and host failures, not routine validation. Functions that access files, networks, processes, GPUs, or devices must declare and receive capabilities. No such host APIs are implemented in compiler 0.3.

## 14. Annotations and metadata
Annotations use @name or @name(key = value). Standard annotations include @deprecated, @test, @entry, @derive, and @requires_capability, subject to compiler support. Unknown annotations are errors unless explicitly declared as metadata-only by the build profile.

## 15. ABI and foreign interfaces
extern declarations may describe host functions but require explicit ABI, ownership, error, and capability rules. The first stable release must define calling convention, layout, alignment, and symbol naming before promising binary compatibility.

## 16. Conformance
A conforming implementation must publish its supported language profile and pass tests for all claimed features. A parser accepting syntax does not prove type-checking or runtime conformance. Compiler 0.3 implements arithmetic expression evaluation only; this draft describes intended language expansion.
